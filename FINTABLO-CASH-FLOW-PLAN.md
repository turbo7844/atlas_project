# Интеграция ДДС с FinTablo

## Результат

- Создать ветку `feature/fintablo-cash-flow` от `main`, не затрагивая текущие untracked-файлы.
- Заменить демонстрационные данные ДДС фактическими операциями FinTablo.
- Загружать данные при старте worker, каждые 5 минут и вручную через существующую кнопку на активной вкладке ДДС.
- Сохранить русский интерфейс, Montserrat и текущие визуальные ограничения Atlas.

## Реализация

- Добавить серверный клиент FinTablo: Bearer-авторизация через `FINTABLO_API_KEY`, запросы `/v1/category`, `/v1/direction` и всех страниц `/v1/transaction?isPlan=0&pageSize=1000&page=N`; таймаут, ограниченные повторы для 429/5xx и диагностический `X-Request-Id` без логирования ключа.
- Миграцией удалить демонстрационную модель/seed ДДС и добавить таблицы текущего снимка FinTablo: статьи, направления, транзакции и состояние синхронизации. Денежные поля хранить как `Decimal`, даты как `Date`, внешние ID и связи — отдельно; полный исходный объект операции сохранять в JSON для полей, не участвующих в отчёте.
- Синхронизацию выполнять как полный нормализованный снимок: сортировка и хеширование, атомарная замена только при изменении, удаление исчезнувших в FinTablo записей, ревизия и `SyncRun`. При ошибке оставлять последнюю успешную версию данных; параллельные ручной и фоновой запуски защищать advisory lock.
- Фактические переводы сохранять в БД, но исключать из KPI и аналитики. Для разделённых операций учитывать дочерние части, исключая родителя из сумм, чтобы не было удвоения.
- Ввести отдельный интервал `FINTABLO_SYNC_INTERVAL_MINUTES=5`; передать ключ и интервал в `web` и `worker`. Worker запускает FinTablo сразу после старта и далее независимо от 30-минутного маркетингового расписания.
- Добавить `GET/POST /api/sync/fintablo-cash-flow` для статуса и ручного запуска, а также `/api/updates/fintablo-cash-flow` для SSE-обновления открытой вкладки после фоновой синхронизации.
- На вкладке ДДС существующая кнопка запускает FinTablo и показывает его время/статус; на остальных вкладках сохраняется текущая логика маркетингового плана. Все сообщения и ошибки остаются русскоязычными.

## ДДС и интерфейсы

- KPI: «Приход», «Расход», «Чистый поток» и «Рентабельность». Рентабельность считать как `(приход − расход) / приход`; при нулевом приходе показывать прочерк. Сравнение с предыдущим равным периодом для рентабельности выводить в процентных пунктах.
- Убрать августовское ограничение для ДДС; `actualThrough` и `lastSyncAt` брать из состояния FinTablo.
- Для выбранного периода и направлений определять пять крупнейших расходных статей. SVG-пайчарт и SVG-линейный график динамики используют одинаковые топ‑5 и агрегат «Прочее», с постоянными цветами внутри выборки.
- Нижняя таблица остаётся по направлениям и получает четыре колонки: приход, расход, чистый денежный поток, рентабельность.
- Добавить направление «Общее» только в фильтр ДДС. Пять существующих направлений сохраняют текущие идентификаторы; операции FinTablo с направлением «Общее», без направления или с неизвестным новым направлением относятся к строке «Общее», при этом исходное направление остаётся сохранено в БД.
- Сделать состояние фильтра направлений отдельным для ДДС: другие вкладки продолжают использовать пять текущих направлений. Старое состояние `localStorage` мигрировать совместимо, а ДДС по умолчанию выбирает все шесть.
- Расширить типы: `CashFlowRow.profitability`, режим дельты KPI в процентных пунктах и согласованные ключи `breakdown`/`series` для топ‑5 статей и «Прочее».
- Добавить в `.env.example` пустой `FINTABLO_API_KEY` и интервал 5 минут; рабочий `.env` не изменять и не коммитить.

## Проверка

- Unit-тесты клиента: Bearer-заголовок, пагинация до неполной страницы, даты, Decimal, некорректный ответ, таймауты и 401/429/5xx.
- Unit-тесты синхронизации: первая загрузка, неизменившийся снимок, изменение/удаление операции, атомарность, сохранение старых данных при сбое и пропуск параллельного запуска.
- Тесты расчётов: фильтры периода и направлений, исключение планов/переводов и родителей split-операций, нулевой приход, формула рентабельности, топ‑5 + «Прочее» и одинаковый состав статей в двух графиках.
- E2E: четыре KPI, пайчарт, динамика статей, таблица, «Общее» только в ДДС, ручное обновление FinTablo, русские toast/error-состояния и тихое обновление через SSE.
- Выполнить `npm test`, `npm run lint`, `npm run build`, затем smoke-проверку через `docker compose up --build` и сверить число/период сохранённых операций с текущим ответом FinTablo.

## Допущения

- Загружается вся доступная история фактических операций, а не только выбранный в интерфейсе период.
- Swagger-файл `docs/FinTablo-v1-swagger.yaml` используется как локальная документация и не изменяется; прочие существующие untracked-файлы также сохраняются.
- На момент проверки доступ к FinTablo рабочий; API возвращает 971 фактическую операцию, 36 статей и 6 направлений. Эти числа не фиксируются в коде.
